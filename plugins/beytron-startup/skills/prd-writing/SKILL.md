# PRD Writing

Use this skill when discovery output must become a PRD or when an existing PRD needs revision.

## Purpose

PRD Writing turns validated discovery into a product contract that design, architecture, Jira, QA, and development can safely use.

## Required Inputs

- Discovery summary or IDEA/RESEARCH artifacts.
- Current approval status.
- Target user and problem statement.
- Business goal and success metrics.
- Known constraints, non-goals, dependencies, and risks.

## PRD Structure

- Overview.
- Problem.
- Target users and personas.
- Goals and non-goals.
- User journeys.
- Functional requirements.
- Non-functional requirements.
- Acceptance criteria.
- Analytics and success metrics.
- Dependencies and risks.
- Open questions.
- Approval status.

## Rules

- Do not write implementation details as requirements unless architecture already approved them.
- Keep acceptance criteria testable.
- Keep non-goals explicit.
- Mark assumptions instead of hiding them.
- Block development until PRD, architecture, tickets, and approval are ready.

## Outputs

- PRD draft.
- PRD revision notes.
- Acceptance criteria.
- Open questions.
- Approval recommendation.
